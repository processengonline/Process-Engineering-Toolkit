Script under test: separator_sizing.py

A second bug (beyond the liquid-retention-length bug already documented and
fixed in the original file) was found and fixed in this version:

  BUG: iterate() selected the optimal trial diameter with a raw
  min(feasible_trials, key=lambda t: t.area_cross * t.selected_length).
  When liquid retention time (not gas capacity or L/D) controls the design,
  area_cross * selected_length is analytically CONSTANT across a wide
  diameter range (it reduces to V_liquid_required / liquid_area_fraction,
  which has no diameter dependence). In that flat region, many trial
  diameters produced volumes agreeing to 14+ significant figures, differing
  only by floating-point rounding noise. The raw min() was effectively
  picking an arbitrary diameter out of the tied region based on which
  trial's rounding error happened to land lowest -- non-deterministic and
  engineering-meaningless. For the exact same default inputs, the ORIGINAL
  (buggy) script selected D=3.00 m / L=8.49 m; this FIXED version
  deterministically selects D=2.50 m / L=12.22 m on every run (verified
  across 3 consecutive runs with identical results).

  FIX: optimal-trial selection now uses a relative-tolerance comparison
  (1e-6) and ties toward the smallest feasible diameter, since the trials
  list is already in ascending-diameter order. This is a deterministic,
  physically sensible tie-break: when several diameters are economically
  identical, prefer the smallest one.

Everything upstream of trial selection (V_max, A_gas, d_min_gas, settling
velocity, oil/water retention volumes, and every individual trial's own
length_gas / length_oil / length_water / length_ld_min / feasibility) is
UNCHANGED and was not affected by this bug -- only which already-computed
trial got chosen as "optimal" was wrong. Both D=3.00m and D=2.50m (and
several diameters in between) are legitimate, code-compliant, PASS-ing
designs with essentially identical vessel volume (~60 m^3 in the
liquid-retention-driven region); the fix simply makes the tool return the
same, smallest-diameter (most conventionally "optimal") answer every time
instead of an arbitrary one.

Nozzle sizes are unaffected by this bug (they depend on flow rates and
target velocities, not on which diameter was selected as optimal) -- but the
INLET NOZZLE size using the un-fixed 3.00 m design vs 2.50 m design happens
to be identical here (15.5 in) since nozzle sizing is independent of vessel
diameter in this tool. Cross-checked: unchanged in this re-run.

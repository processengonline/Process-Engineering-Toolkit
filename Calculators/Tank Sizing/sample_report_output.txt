================================================================================
TANK SIZING CALCULATOR - SAMPLE TEST REPORT
Script under test: tank_sizing.py
Test date: 2026-08-09
Python: 3.12.3
================================================================================

SUMMARY
-------
10 test cases executed: 6 successful calculation runs (diameter+height ->
volume, target_volume solved both directions, JSON file input, dual-assume
priority check) plus 4 edge/error cases. All numeric results were
independently hand-verified against the module's own cylinder-volume and
area formulas (see Verification Notes) and matched exactly. However, testing
surfaced a real, fairly significant bug: negative diameter or height values
are NOT validated anywhere on the diameter+height path, and are silently
accepted, producing internally INCONSISTENT results (e.g. a positive volume
but a negative shell area from the same negative diameter) rather than an
error. A second, lower-severity inconsistency was also found: diameter=0 or
height=0 is rejected, but with a misleading "insufficient inputs" message
rather than a specific "must be positive" message. Both are detailed below.


--------------------------------------------------------------------------------
TEST 1 - Diameter + height -> volume (baseline)
--------------------------------------------------------------------------------
Scenario: 10 m diameter x 8 m height cylindrical tank.

Command:
  python3 tank_sizing.py --diameter 10 --height 8

Output:
  Tank sizing results:
   - volume_m3: 628.319
   - volume_liters: 628319
   - volume_gal_us: 165984
   - volume_barrels: 3952
   - shell_area_m2: 251.327
   - roof_area_m2: 78.5398
   - bottom_area_m2: 78.5398
   - mass_kg: 628319

Result: PASS
Notes:
  - vol = pi*(D/2)^2*H = pi*25*8 = 628.319 m3 -> matches.
  - shell = pi*D*H = pi*10*8 = 251.33 m2 -> matches.
  - roof = pi*D^2/4 = pi*100/4 = 78.54 m2 -> matches.
  - mass = vol*density(default 1000) = 628,319 kg -> matches.

--------------------------------------------------------------------------------
TEST 5 - Validation gap: diameter or height = 0
--------------------------------------------------------------------------------
Scenario: A zero diameter or zero height is physically meaningless and should
be rejected with a specific, actionable error.

Commands:
  python3 tank_sizing.py --diameter 0 --height 8
  python3 tank_sizing.py --diameter 10 --height 0

Output (stderr, both cases):
  Error: Insufficient inputs: provide diameter+height OR
  target_volume+assume_height/assume_diameter

Exit code: 2 (both cases)

Result: PASS functionally (script does reject the input and exits cleanly),
but FLAGGED for a misleading message — see Observation 2.
Notes:
  - compute_from_args() uses "if inputs.diameter and inputs.height:" — a
    Python truthiness check, not "is not None". Since 0.0 is falsy in
    Python, diameter=0 or height=0 causes the whole branch to be skipped,
    and the code falls through all the way to the final catch-all
    "Insufficient inputs" error — which is misleading, since the user DID
    provide both diameter and height; the actual problem is that one of
    them is zero, and that specific reason is never reported.


--------------------------------------------------------------------------------
TEST 6 - BUG: negative diameter silently accepted, produces INCONSISTENT
results (positive volume, negative shell area)
--------------------------------------------------------------------------------
Scenario: A negative diameter is not physically meaningful and should be
rejected, but the truthiness check ("if inputs.diameter and ...") treats any
nonzero number — including negative ones — as valid, so it proceeds straight
into the calculation with no sign check anywhere in the diameter+height path.

Command:
  python3 tank_sizing.py --diameter -5 --height 8

Output:
  Tank sizing results:
   - volume_m3: 157.08
   - volume_liters: 157080
   - volume_gal_us: 41496
   - volume_barrels: 988.001
   - shell_area_m2: -125.664
   - roof_area_m2: 19.635
   - bottom_area_m2: 19.635
   - mass_kg: 157080

Exit code: 0 (no error at all)

Result: FAIL - real bug (see Observation 1)
Notes:
  - volume_cylinder() uses radius = D/2 then radius*radius, so the negative
    sign cancels and produces a POSITIVE (and numerically "plausible") volume
    of 157.08 m3 -- silently masking the invalid input.
  - area_shell() uses A = pi*D*H directly (D not squared), so the negative
    sign survives and produces a NEGATIVE shell area of -125.664 m2 in the
    very same result set.
  - Net effect: the tool returns a self-contradictory report — a tank with a
    positive volume and mass, but a negative shell surface area — with no
    warning or error at all. A user skimming the output for volume/mass
    could easily miss the negative shell area and use these numbers directly
    (e.g. for insulation or paint-area estimates) without ever realizing the
    input was invalid.

   - bottom_area_m2: 50.2655
   - mass_kg: -251327

Exit code: 0 (no error at all)

Result: FAIL - same bug class as Test 6 (see Observation 1)
Notes:

    linearly), so volume, volume conversions, and mass are ALL negative,
    while roof/bottom areas (which don't depend on H) remain positive. Again,
    no validation error is raised anywhere — confirms the missing
    diameter/height positivity check is systemic across the whole
    diameter+height branch, not specific to one variable.


--------------------------------------------------------------------------------
TEST 8 - Priority check: both --assume-height and --assume-diameter given
--------------------------------------------------------------------------------
Scenario: The dataclass/CLI allow both assume_height and assume_diameter to
be supplied simultaneously alongside target_volume. The code checks
assume_height first, so it should take priority and assume_diameter should
be silently ignored.

Command:
  python3 tank_sizing.py --target-volume 100 --assume-height 5 \
      --assume-diameter 3

Output:
  Tank sizing results:
   - solution_diameter_m: 5.04627
   - solution_height_m: 5
   - volume_m3: 100
   - shell_area_m2: 79.2665
   - roof_area_m2: 20
   - bottom_area_m2: 20
   - mass_kg: 100000

Result: PASS (behaves as coded), flagged as a usability note
Notes:
  - solution_height_m = 5 (the --assume-height value) confirms assume_height
    took priority; the supplied --assume-diameter 3 was silently discarded
    rather than solved-for or cross-checked. radius^2 = 100/(pi*5) = 6.3662;
    D = 2*sqrt(6.3662) = 5.046 -> matches, confirming the calculation used
    assume_height as documented. This matches the code's if/elif order, so
    it is not a functional bug, but a user who supplies both values (perhaps
    by mistake, or expecting a validation error) gets no indication that one
    of their two inputs was ignored. See Observation 3.

agree with the script's output in every case, confirming volume_cylinder(),

================================================================================
OBSERVATIONS / RECOMMENDATIONS
================================================================================
1. BUG (Tests 6-7, HIGH priority, recommend fixing): There is no validation
   anywhere in the diameter+height branch of compute_from_args() that
   diameter and height are positive. Because volume/roof/bottom-area
   formulas use diameter or height squared (sign cancels) while the shell
   area formula uses them linearly (sign survives), a negative input
   produces a self-contradictory result set (e.g. positive volume/mass but
   negative shell area, or vice versa) with NO error and NO warning. This is
   more serious than a simple crash, since the tool returns numbers that
   look superficially plausible and could be used downstream (e.g. for
   insulation sizing, coating area, or heat-loss estimates) without the user
   ever realizing the input was invalid. Recommend adding an explicit
   "if diameter <= 0 or height <= 0: raise ValueError(...)" guard at the top
   of the diameter+height branch (and equivalent guards on the
   target_volume/assume_* branch, e.g. in diameter_for_volume() and
   height_for_volume(), which currently only check for a negative
   radius-squared rather than validating raw inputs directly).
2. INCONSISTENT ERROR MESSAGE (Test 5, medium priority): The
   "if inputs.diameter and inputs.height:" check uses Python truthiness, so
   diameter=0 or height=0 is treated the same as "not provided," producing
   the generic "Insufficient inputs" message instead of a specific
   "diameter/height must be greater than zero" message. Fixing Observation 1
   with explicit positivity checks (using "is not None" for presence and a
   separate "<= 0" check for validity) would naturally resolve this too.
3. USABILITY NOTE (Test 8, low priority, not a bug): When both
   --assume-height and --assume-diameter are supplied alongside
   --target-volume, --assume-height silently wins and --assume-diameter is
   discarded with no warning. This matches the code's documented if/elif
   order and is not incorrect, but a warning/note in the output (e.g.
   "assume_diameter ignored because assume_height was provided") would help
   a user catch an accidental double-entry.
4. PyYAML was not installed in the test environment, so only the JSON input
   path (Test 4) was exercised; the YAML path raises a clear RuntimeError
   with an install hint if PyYAML is missing (correct defensive behavior,
   not separately exercised here).

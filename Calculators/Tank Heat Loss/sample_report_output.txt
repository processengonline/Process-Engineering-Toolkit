================================================================================
TANK HEAT LOSS CALCULATOR - SAMPLE TEST REPORT
Script under test: tank_heat_loss.py
Test date: 2026-08-09
Python: 3.12.3
================================================================================

SUMMARY
-------
10 test cases executed: 6 successful calculation runs (insulated tank, bare
tank, JSON input, CLI bottom-present flag, reversed temperature gradient)
plus 4 cases that surfaced problems. All successful-case numeric results
were independently hand-verified against the module's own U-value and heat
loss formulas (see Verification Notes) and matched exactly. Two real, fairly
significant bugs were found:
  (1) calculate() is NOT wrapped in a try/except in main(), so any
      calculation-time error (e.g. hi=0, ho=0, or ins_k=0 with insulation
      present) crashes with a raw, user-facing Python traceback and exit
      code 1, instead of the clean "Calculation error" + controlled exit
      code pattern used elsewhere in this codebase (Tests 6-7).
  (2) bottom_present is handled inconsistently between the CLI and the JSON
      input file: the CLI uses a proper string-to-bool parser, but JSON
      input just does bool(value), so a JSON file with "bottom_present":
      "false" (a string) is silently treated as True — the classic Python
      "any non-empty string is truthy" trap (Test 5).
A third, lower-severity issue (silent handling of negative insulation
thickness) is noted at the end.

--------------------------------------------------------------------------------
TEST 5 - BUG: bottom_present as a JSON string "false" is silently treated
as True
--------------------------------------------------------------------------------
Scenario: Same tank/bottom-exclusion intent as Test 4, but bottom_present is
supplied as the JSON string "false" rather than through the CLI flag —
exercising Python's bool(str) truthiness trap.

Input file (heatloss_bottom_false.json):
{
  "diameter": 10,
  "height": 8,
  "product_temp": 60,
  "ambient_temp": 20,
  "bottom_present": "false"
}

Command:
  python3 tank_heat_loss.py --inputs heatloss_bottom_false.json

Output:
  Calculation results:
   - Abottom_m2: 78.540    <-- should be 0.000, matching Test 4's intent
   - Atotal_m2: 408.407
   - Q_bottom_W: 15707.963  <-- should be 0.000
   - Q_total_W: 81681.409
   - Energy_kWh_per_day: 1960.354
   - Heating_duty_W (with safety factor): 93933.620

Result: FAIL - real bug (see Observation 1)
Notes:
  - _args_to_inputs() builds the dataclass with
    "bottom_present=bool(data.get('bottom_present', True))". When the value
    comes from a JSON file as the string "false", bool("false") evaluates to
    True in Python, because any non-empty string is truthy — only bool("")
    is False. The bottom is therefore silently INCLUDED even though the user
    explicitly wrote "false".
  - This is especially deceptive because the exact same user intent, entered
    via --bottom-present false on the CLI (Test 4), works correctly — the
    CLI path uses a dedicated string-parsing lambda, but the JSON/file path
    does not reuse it and instead applies a raw bool() cast. A user who is
    used to editing JSON config files (a documented, supported input method)
    has no way to know this silently fails; the tool runs successfully and
    reports plausible-looking numbers.


--------------------------------------------------------------------------------
TEST 6 - BUG: hi = 0 crashes with an unhandled Python traceback
--------------------------------------------------------------------------------
Scenario: Internal heat transfer coefficient set to zero (e.g. accidental
default/placeholder value), which makes the 1/hi term in overall_u_value()
divide by zero.

Command:
  python3 tank_heat_loss.py --diameter 10 --height 8 --product-temp 60 \
      --ambient-temp 20 --hi 0 --ho 10

Output (stderr):
  Traceback (most recent call last):
    File "tank_heat_loss.py", line 216, in <module>
      main()
    File "tank_heat_loss.py", line 211, in main
      results = calculate(inputs)
    File "tank_heat_loss.py", line 104, in calculate
      U_shell = overall_u_value(...)
    File "tank_heat_loss.py", line 75, in overall_u_value
      r_total = (1.0 / hi) + (1.0 / ho)
  ZeroDivisionError: float division by zero

Exit code: 1

Result: FAIL - real bug (see Observation 2)
Notes:
  - main() wraps ONLY the input-building step
    ("inputs = _args_to_inputs(args)") in a try/except; the subsequent
    "results = calculate(inputs)" call has no error handling at all. Any
    exception raised during calculation — division by zero, invalid math,
    etc. — propagates all the way up and prints a raw Python traceback to
    the end user, with a generic exit code 1, rather than a clean
    "Calculation error: ..." message and a controlled exit code (as seen
    consistently in the other scripts tested in this series, e.g.
    psv_sizing.py, line_hydraulics.py, control_valve_sizing.py, and
    pump_hydraulics.py, all of which wrap their calculate()-equivalent call
    in its own try/except).

TEST 7 - Confirms Test 6 is systemic: ins_k = 0 with insulation present
--------------------------------------------------------------------------------
Scenario: Insulation thickness > 0 but thermal conductivity set to 0 (e.g. a
data-entry slip), which divides by zero in the (ins_thickness/ins_k) term.

Command:
  python3 tank_heat_loss.py --diameter 10 --height 8 --product-temp 60 \
      --ambient-temp 20 --ins-thickness 0.05 --ins-k 0 --hi 10 --ho 10

Output (stderr): same class of unhandled ZeroDivisionError traceback as
Test 6, this time raised at "r_total = (1.0/hi) + (ins_thickness/ins_k) +
(1.0/ho)"

Exit code: 1

Result: FAIL - same bug class as Test 6 (see Observation 2)
Notes:
  - Confirms the missing try/except around calculate() is a systemic gap,
    not specific to the hi=0 case — any of hi=0, ho=0, or (ins_thickness>0
    with ins_k=0) will crash the same way.


--------------------------------------------------------------------------------
TEST 8 - Negative insulation thickness (silently reinterpreted, not
crashed)
--------------------------------------------------------------------------------
Scenario: A negative insulation thickness is physically meaningless.

Command:
  python3 tank_heat_loss.py --diameter 10 --height 8 --product-temp 60 \
      --ambient-temp 20 --ins-thickness -0.05 --ins-k 0.04 --hi 10 --ho 10

Output:
  Calculation results:
   - U_shell_W_m2K: 5.000
   - Q_total_W: 81681.409
   (identical to Test 2's bare-tank result)

Exit code: 0

Result: PASS functionally (no crash, no numerically nonsensical output),
flagged as a minor input-handling note — see Observation 3.
Notes:
  - overall_u_value()'s guard is "if ins_thickness <= 0.0: ... (negligible
    conduction)", so a negative thickness happens to fall into the same
    branch as "no insulation" and produces the same (valid-looking) result
    as Test 2. This avoids a crash or a nonsensical negative-U result, but
    it does so by silently reinterpreting a physically invalid negative
    input as "zero insulation" with no warning that the input itself was
    invalid.

   - Q_roof_W: -1354.135

   - Q_total_W: -7041.501
   - Energy_kWh_per_day: -168.996

================================================================================
OBSERVATIONS / RECOMMENDATIONS
================================================================================
1. BUG (Test 5, HIGH priority, recommend fixing): JSON/YAML file input for
   bottom_present uses a plain bool(value) cast, so a JSON string value like
   "false" is silently treated as True (any non-empty string is truthy in
   Python). This directly contradicts the correct behavior of the
   corresponding CLI flag, which uses a proper string-parsing lambda.
   Recommend normalizing bottom_present the same way regardless of source —
   e.g. reuse a shared "truthy-string" parser for both the CLI default and
   the file-loaded value, or explicitly check
   "str(value).lower() in ('1','true','yes')" when the loaded value is a
   string, while still accepting native JSON booleans (true/false) as-is.
2. BUG (Tests 6-7, HIGH priority, recommend fixing): main() does not wrap
   "results = calculate(inputs)" in a try/except, unlike the other scripts
   reviewed in this series. Any calculation-time error (hi=0, ho=0, ins_k=0
   with insulation present, or any other future numerical edge case) exposes
   a raw Python traceback to the end user with exit code 1, rather than the
   clean "Calculation error: ..." message with a controlled exit code (2 or
   3) used elsewhere. Recommend wrapping the calculate() call in the same
   try/except pattern already used around _args_to_inputs(), and optionally
   adding explicit validation in overall_u_value() for hi>0, ho>0, and
   (ins_k>0 when ins_thickness>0) to produce clearer messages than a bare
   ZeroDivisionError.
3. MINOR (Test 8, informational): Negative insulation thickness is silently
   folded into the "no insulation" branch rather than rejected. This avoids
   a crash and avoids nonsensical output, so it's not urgent, but a small
   explicit check ("if ins_thickness < 0: raise ValueError(...)") would make
   the invalid-input case explicit rather than implicit.
4. PyYAML was not installed in the test environment, so only the JSON input
   path (Tests 3 and 5) was exercised; the YAML path (_parse_inputs_from_file)
   raises a clear RuntimeError with an install hint if PyYAML is missing
   (correct defensive behavior, not separately exercised here). Note also
   that _parse_inputs_from_file() returns yaml.safe_load(fh) directly without
   the "or {}" fallback used on the JSON branch — an empty YAML file would
   return None instead of {}, which would then fail later with a less clear
   error; not exercised here since PyYAML was unavailable, but worth a
   consistency check if YAML support is used in practice.

SUMMARY
-------
12 test cases executed: 7 successful calculation runs (hydraulic/shaft power,
flow unit conversions via m3/h and L/s CLI flags, power->head, NPSH margin,
JSON file input) plus 5 error/edge cases. All numeric results were
independently hand-verified against the module's own power, head, and NPSHr
formulas (see Verification Notes) and matched exactly. One real bug was found:
the --flow-gpm CLI flag is accepted by argparse but silently discarded — it is
never converted to flow_m3_s, so using it alone produces a "Flow is required"
error with no indication that the flag itself is non-functional (Test 7).
A secondary, lower-severity observation on zero-flow handling is noted at the
end (Test 12).


--------------------------------------------------------------------------------
TEST 1 - Flow + head + efficiency -> hydraulic/shaft power
--------------------------------------------------------------------------------
Scenario: 0.05 m3/s water at 30 m head, 75% efficiency — standard sizing
duty point.

Command:
  python3 pump_hydraulics.py --flow-m3s 0.05 --head 30 --efficiency 0.75

Output:
  Pump hydraulics results:
   - hydraulic_power_W: 14710
   - shaft_power_W: 19613.3
   - shaft_power_kW: 19.6133
   - shaft_power_HP: 26.3019
   - flow_m3_s: 0.05
   - flow_m3_h: 180
   - flow_L_s: 50
   - flow_gpm_us: 792.516
   - npshr_estimated_m: 13.6326

Result: PASS
Notes:
  - P_hyd = rho*g*Q*H = 1000*9.80665*0.05*30 = 14,710 W -> matches.
  - P_shaft = 14,710/0.75 = 19,613.3 W -> matches.
  - HP = 19,613.3/745.699872 = 26.302 -> matches.
  - flow_gpm = 0.05*15,850.3231 = 792.52 -> matches.
  - NPSHr: Q_norm = 0.05/0.01 = 5; NPSHr = 0.5+5*5^0.6 = 13.63 -> matches.

--------------------------------------------------------------------------------
TEST 7 - BUG: --flow-gpm CLI flag is accepted but silently non-functional
--------------------------------------------------------------------------------
Scenario: Flow supplied ONLY via --flow-gpm (the CLI help text itself already
hints at the issue: "Flow (US gpm) -- not used directly").

Command:
  python3 pump_hydraulics.py --flow-gpm 500 --head 30

Output (stderr):
  Calculation error: Flow (flow_m3_s) is required

Exit code: 2

Result: FAIL (real bug — see Observation 1)
Notes:
  - Unlike --flow-m3h and --flow-Ls, which both have explicit conversion
    blocks in _args_to_inputs() that populate data['flow_m3_s'], there is NO
    equivalent block for args.flow_gpm. The flag is parsed by argparse (dest
    'flow_gpm') but the resulting value is never read anywhere in
    _args_to_inputs() or calculate().
  - Net effect: a user who runs the tool with only --flow-gpm gets a generic
    "Flow is required" error, which is confusing — the flag exists, is
    documented in --help, and accepts a value, but has no effect at all.

================================================================================
OBSERVATIONS / RECOMMENDATIONS
================================================================================
1. BUG (Test 7, recommend fixing): --flow-gpm is defined as a CLI argument
   and even documented in its own help text as "not used directly," but this
   is effectively a silent dead flag — argparse accepts and parses it, yet
   _args_to_inputs() never reads args.flow_gpm to populate flow_m3_s (it only
   does this for args.flow_m3h and args.flow_l_s). A user relying on this
   flag alone will get an unrelated "Flow is required" error with no hint
   that the flag they used is the actual cause. Recommend either (a) wiring
   up a conversion block analogous to the m3/h and L/s cases (US gpm -> m3/s
   is 1/15850.3231), or (b) removing the flag/argument entirely and updating
   the help text and docstring, to avoid a documented-but-nonfunctional
   option in the public CLI.
2. MINOR (Test 12, informational): calculate() validates Q>0 on the
   power->head branch (via head_from_power_and_flow) and on efficiency, but
   not on the head->power branch (hydraulic_power_W has no Q>0 guard). A
   flow of 0 silently returns an all-zero result set instead of raising a
   validation error, which is inconsistent with how the power->head branch
   handles the same input. Not incorrect physics, but worth a consistency
   pass if the intent is to flag non-physical/degenerate duty points
   uniformly across both branches.
3. estimate_npshr() is explicitly documented as "a rough placeholder for
   demonstration" with a simple empirical scaling — this matches its
   observed behavior and is not a defect, but underscores (consistent with
   the module's own docstring) that real NPSHr values must come from vendor
   pump curves, not this formula.
4. PyYAML was not installed in the test environment, so only the JSON input
   path (Test 6) was exercised; the YAML path raises a clear RuntimeError
   with an install hint if PyYAML is missing (correct defensive behavior,
   not separately exercised here).
